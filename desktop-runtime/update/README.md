# Desktop releases

1. Set the repository and desktop version in `release/desktop-channel.json`. Set a new numeric version for each release. Build, sign as applicable, and test the exact ZIPs for distribution. The Windows launcher embeds its runtime inventory. Keep the matching inventory in `desktop-runtime/windows/native/Launcher/runtime.sha256`. [Native Windows packaging](../windows/native/README.md)
2. Place the accepted `OpenX6-macOS-arm64.zip`, `OpenX6-Windows11-x64-native.zip` and their original `SHA256SUMS` together. Commit an exact copy of the reviewed checksum file as `release/desktop-SHA256SUMS` in the release checkout. Run `python3 desktop-runtime/update/check_release.py /path/to/assets` with Python 3.11 or later. It validates the accepted archive hashes, Mac identity and ZIP integrity, Windows runtime inventory, launcher manifest and native worker sources.
3. When ready to publish, attach those three files to a draft stable GitHub Release. Push the matching version tag at the reviewed commit. The workflow downloads the draft assets by ID, checks their sizes and GitHub digests, runs the same verifier, and rechecks the draft inventory before publishing. Rehearsing the Python check locally requires no GitHub credentials.
4. Both desktop apps check stable releases at startup. Choose File → Update to install a newer release. Windows starts the downloaded launcher through the system shell and activates it after its GUI opens. Users of either platform can follow the manual instructions in the main README. Desktop updates preserve the Holder. Camera updates require a separate SD build and install.

For each Mac release, sign the app and nested executable code with Developer ID, hardened runtime and secure timestamps. Submit the newly signed ZIP to Apple notarization and require an Accepted result. Staple the ticket to the app, then create the final distribution ZIP. Extract that final ZIP and verify it with `codesign --verify --deep --strict`, `xcrun stapler validate`, and `spctl --assess --type execute -vv`; Gatekeeper must report `accepted` and `source=Notarized Developer ID`. Calculate the release checksums only after these steps. An earlier version's notarization does not cover a changed app.

Also test an actual update from the previously released Mac app. Open the downloaded app through Launch Services with quarantine intact, wait for its UI to create the version-local `ready` marker, then close it and reopen the old entry. That entry must launch the new version. Compare the existing Holder, module cache and language preference before and after. App Translocation can change the filesystem device identifier; the readiness check accepts a relocated copy only after verifying both sealed Developer ID bundles and matching their signed identity. A direct call with the installed path alone does not test this case.
